﻿Socratic methodology Kernel


Yes. The clean way to hold all of this together is to separate mathematical interchangeability, benchmark admissibility, and execution-path reachability. They are three different propositions.


1. Experiment A vs. the rejected 3.94×


The decisive issue is not simply target-cpu. There are two separate questions:


1. Is the measurement reproducible from a preserved primary receipt?




2. Does that receipt satisfy the standing benchmark contract?






Experiment A passes both.


The audit identifies:


a specific evidence ID: experiment_a_afea62bc


a specific evidence commit: 8df0c247


a preserved evidence directory


raw Criterion output


disassembly


hardware profile


provenance record


SHA256SUMS, independently verified


explicit -C target-cpu=x86-64




So 7.23× and 4.42× are not numbers inferred from a report. They are measurements recoverable from a sealed evidence package.


The 3.94× result fails at a more fundamental level. Its original receipt/harness is unavailable, and the audit establishes that the historical implementation used the wrong DIT/DIF semantic interpretation. BENCHMARKS.md, CLAIM_MATRIX.md, and the other surviving documents therefore function as descriptions of an old result, not as a presently reproducible primary receipt.


So I would phrase the methodological distinction precisely as:


> Experiment A is an admissible measurement because its exact experimental state, execution output, provenance, and integrity manifest survive as a verifiable primary evidence package under the explicit-target benchmark contract. The 3.94× figure survives only as a historical observation because the experimental receipt/harness needed to reproduce and independently validate it does not.






target-cpu matters because the 3.94× evidence also fails the current semantic/measurement chain, but "different target-cpu" alone is not the reason 3.94× is rejected.


That distinction is important.




---


2. The theorem-count universes


This is a classic scope-of-quantification problem.


Saying:


> "There are 33 theorems"






is incomplete.


Saying:


> "There are 87 theorems"






is also incomplete.


The actual proposition needs the universe:


> There are 87 theorem declarations in the .lean files of tscp-anchor at the specified state.






That is a different proposition from:


> There are 83 entries represented by the proof-to-code correspondence map.






And different again from:


> There are 33 theorems in the historical Montgomery/formalization universe described by EVIDENCE_CHAIN.md.






The number is not the claim. The number plus its universe is the claim.


What should a reviewer do at cdfccf03?


The reviewer should not choose among 33, 83, and 87 by intuition.


They should ask:


> What proposition is B7 actually making about formal verification?






If B7 says:


> "The repository currently contains 87 Lean theorem declarations."






then the reviewer checks the frozen checkout and machine-counts them.


If B7 says:


> "The proof-to-code correspondence layer contains 83 mapped proofs."






then proof-to-code-map.md is the relevant artifact.


If B7 says:


> "The Montgomery arithmetic foundation contains 33 formally documented results."






then the relevant evidence must define that 33-element universe.


Therefore, 87 is not automatically the "correct" B7 number. It is the correct answer only to the proposition whose universe is all current theorem declarations in tscp-anchor.


For B7, I would avoid presenting a bare theorem count entirely unless the claim being made actually needs one.




---


3. Chain 1: what source evidence would prove it already exists?


Start with the abstraction boundary.


Plonky3's DFT machinery is built around TwoAdicSubgroupDft<F>. The public repository describes radix-2 DIT, Bowers, four-step, and other interpolation strategies as distinct implementations within the DFT layer. 


The key question is therefore not:


> "Does ZkshaDifAdapter compile?"






It is:


> Does an object containing the adapter actually become the DFT implementation used by a real proving configuration?






A source-only Chain-1 trace would look approximately like:


Proof configuration
      ↓
PCS / FRI configuration
      ↓
TwoAdicSubgroupDft<F>
      ↓
concrete DFT implementation
      ↓
Butterfly<F>
      ↓
ZkshaDifAdapter
      ↓
Phase-2.5 fused Montgomery operation
      ↓
AVX-512 implementation


Positive evidence


A frozen checkout could establish Chain 1 without new performance numbers if it contains all of the following relationships.


A. Adapter definition


Something equivalent to:


impl Butterfly<BabyBear> for ZkshaDifAdapter { ... }


or an equivalent concrete implementation.


B. Adapter construction


A configuration site actually constructs it:


let dft = ...
    ZkshaDifAdapter::new(...);


The existence of the type alone isn't enough.


C. DFT ownership/injection


That object must be supplied to the concrete DFT implementation that the prover actually uses.


For example, conceptually:


prover config
    → PCS config
       → DFT object
          → adapter


D. Prover configuration


There must be an actual proving configuration—not merely a unit-test configuration—that selects this path.


E. Proof entry point


An example, integration test, executable, or proof-generation function must invoke the proving stack with that configuration.


F. Reachability


The source graph must connect those objects. Ideally, an existing execution trace, instrumentation receipt, or test assertion would remove ambiguity about dynamic dispatch/generic selection.


That gives you a genuine construction-and-reachability chain.




---


4. What would constitute negative evidence?


There are several progressively stronger forms.


Weak negative


You find:


ZkshaDifAdapter


but only in:


its own module


unit tests


benchmarks


dead/example code


documentation




That establishes implementation existence, not prover reachability.


Stronger negative


The adapter implements Butterfly, but no configuration constructs it.


Then:


> Butterfly compatibility: demonstrated.
Prover reachability: not demonstrated.






Strong negative


The adapter is constructed somewhere, but no path connects that object to the TwoAdicSubgroupDft used by the PCS/prover.


Again:


> Constructible: yes.
Selected by prover: no evidence.






Decisive negative for the frozen checkout


If exhaustive source tracing finds:


adapter definition
        ↓
tests/benchmarks only


and no construction site feeding any prover DFT/PCS configuration, then the frozen checkout contains no source-level Chain 1.


That is enough to preserve:


> Kernel implementation and kernel receipt: proven.
Real prover integration: not demonstrated.






It does not prove that integration is impossible. It proves that this frozen artifact does not establish it.


That distinction is exactly what you want.




---


5. What evidence upgrades "not demonstrated" to "integrated"?


You need evidence of execution, not merely compatibility.


At minimum:


Static evidence


adapter source


Butterfly implementation


construction site


DFT selection site


prover/PCS configuration


proof-generation entry point




Dynamic evidence


At least one of:


an existing execution trace showing the adapter was invoked;


an instrumentation receipt showing calls crossed the adapter boundary;


a proof-generation test whose configuration demonstrably selects the adapter;


an independently inspectable generated proof tied to that configuration.




The strongest version is:


configuration identity
       +
adapter identity
       +
proof invocation
       +
adapter invocation evidence
       +
successful proof


Notice what is not required for the integration proposition:


> A speedup.






A proof generated through the adapter is evidence of integration even if the adapter is slower.


That is why the 0.994× B5 result and the 7.23× kernel result should remain separate claims.




---


6. Why you should not manufacture that evidence casually on phase-2.5


This is the governance point.


cdfccf03 is a frozen Phase-2.5 state. If you modify it to create the missing integration path, then the resulting proof is no longer evidence about the frozen Phase-2.5 artifact.


You would have changed:


FROZEN STATE
cdfccf03


into:

7. The central Plonky3 abstraction


This is the important conceptual bridge.


TwoAdicSubgroupDft<F> is the abstraction that says, essentially:


> Given a field with the appropriate two-adic structure, provide the operations required to transform matrix-valued polynomial evaluations over a two-adic subgroup and perform the corresponding coset LDE operations.






That is why an external implementation can participate at all.


The prover doesn't fundamentally care whether the underlying DFT is:


Radix2Dit


Radix2DitParallel


Radix2Bowers


Radix2DFTSmallBatch


RecursiveDft


or another conforming implementation.




It cares that the object satisfies the required DFT contract.


That is the abstraction boundary.


But there is a second boundary underneath it:


TwoAdicSubgroupDft
        ↓
Butterfly


A concrete radix-2 implementation decomposes its work into butterfly operations.


So an external adapter implementing the appropriate Butterfly<F> can be mathematically interchangeable only if its semantics match the butterfly contract actually being invoked.




---


8. DIF versus DIT


The distinction is not cosmetic.


You gave the essential formulas:


DIF


\[
(a,b)\mapsto
(a+b,\;(a-b)\omega)
\]


DIT


\[
(a,b)\mapsto
(a+b\omega,\;a-b\omega)
\]


They distribute the twiddle multiplication differently.


Therefore an adapter implementing a DIF butterfly cannot simply be substituted for a DIT butterfly because both happen to implement:


Butterfly<F>


The trait is the interface. The implementation's semantic contract still matters.


This is precisely why the historical 3.94× result is dangerous: a benchmark can produce a perfectly plausible number while measuring the wrong transform semantics.


So:


> Trait compatibility ≠ algorithmic equivalence.






That is one of the most important lessons in this entire audit.

9. Twiddle generation


Here the structure is straightforward.


A radix-2 DFT needs powers of an appropriate root of unity.


The field supplies the relevant two-adic root/generator machinery. BabyBear, for example, declares two-adic data including its two-adicity and generator table. 


The DFT implementation then obtains an appropriate root and expands it into the powers required by the butterfly stages.


The important conceptual distinction is:


field
  ↓
root of unity
  ↓
powers of root
  ↓
twiddle table
  ↓
butterfly


The exact root representation need not necessarily be byte-for-byte identical between two mathematically correct implementations.


What matters is semantic compatibility:


\[
\omega^n = 1
\]


with the appropriate order and the exact convention required by the DFT algorithm.


So an external adapter does not inherently need the identical memory layout or table-generation routine.


But it must use roots whose:


order,


orientation,


stage interpretation,


indexing,


and transform convention




match the Plonky3 path it is replacing.


Otherwise you get another version of the DIT/DIF problem.


Why cache the table?


Because twiddle generation is setup work that can be reused across repeated transforms of the same subgroup size.


A cache keyed by log_h means, conceptually:


log_h = 20
    ↓
construct twiddles once
    ↓
reuse for subsequent transforms of height 2^20


That matters enormously in a prover because the same transform sizes can occur repeatedly.


The cache therefore separates:


> twiddle preparation cost






from:


> repeated transform execution cost.

10. BabyBear's Montgomery parameters


The current Plonky3 source identifies BabyBear as:


PRIME    = 0x78000001
MONTY_MU = 0x88000001
MONTY_BITS = 32


and defines:


BabyBear = MontyField31<BabyBearParameters>






PRIME is the field modulus:


\[
p=2^{31}-2^{27}+1.
\]


MONTY_MU is the Montgomery reduction parameter used by the underlying MontyField31 arithmetic.


That matters because the butterfly's multiplication isn't an abstract operation anymore at the implementation level:


twiddle multiplication
        ↓
Montgomery multiplication/reduction
        ↓
packed field arithmetic

11. Why the AVX-512 packing matters


Plonky3 has architecture-specific implementations for BabyBear, including AVX2, AVX-512, and NEON. The project's public status explicitly lists those vectorized BabyBear implementations. 


The AVX-512 path packs multiple field elements into a vector register and performs the arithmetic across those lanes.


For the SimdField<16> style used by the Phase-2.5 work, the important fact is:


> One vector operation represents 16 BabyBear field elements.






That is the natural shape of the optimization.


A scalar butterfly:


a0,b0
a1,b1
a2,b2
...


can instead become conceptually:


A = [a0 ... a15]
B = [b0 ... b15]


vector butterfly(A, B)


The arithmetic throughput is therefore no longer determined solely by the number of scalar field operations. It is determined by:


packing/unpacking,


vector arithmetic,


Montgomery reduction,


memory movement,


twiddle loading,


and how much independent work exists to fill the lanes.

12. What dominates an isolated butterfly benchmark?


If the twiddle table is already generated and resident—as it should be for a kernel benchmark—the answer is:


> The arithmetic and data movement that execute the butterflies, not twiddle-table generation.






Twiddle generation is amortized setup.


That distinction is essential when interpreting the Experiment A result.


A kernel benchmark answering:


> "How quickly can this implementation execute already-prepared butterfly work?"






is not answering:


> "How much faster is a complete STARK proof?"






The latter includes:


trace generation
→ constraint evaluation
→ polynomial operations
→ DFT/LDE
→ commitments
→ FRI
→ hashing
→ proof assembly


The DFT is one component.


And even inside DFT:


twiddle preparation
+
matrix movement
+
transpose/reordering
+
butterflies
+
parallel scheduling
+
LDE operations


all contribute.

13. What the existing Criterion suite actually tells you


The DFT benchmark suite is fundamentally a DFT-strategy benchmark.


It can tell you things such as:


> Given this field, transform size, implementation strategy, batch width, and LDE operation, how does this DFT implementation perform relative to another?






It does not automatically establish:


> "Replacing this butterfly makes the full prover X% faster."






That would require crossing the abstraction boundary into actual proving.


Plonky3 itself emphasizes that the DFT layer is one component among the larger PIOP/STARK toolkit, while its examples provide actual proof-generation entry points.
