﻿SPRIFES


There’s a useful correction to make to the previous decomposition.


EVIDENCE, RELATIONSHIP, and SPRIFES


There’s a useful correction to make to the previous decomposition.


EVIDENCE, RELATIONSHIP, and INTEGRITY are not yet equally mature candidates. The underlying concepts are promising, but the acronym quality and formal role differ. More importantly, we should not let the names outrun the objects.


The emerging ontology


I would currently separate the vocabulary into four kinds of things:


Name Candidate formal role Core question


FOLLOW transition/reachability relation Can this path legitimately be followed?
PROPER admissibility predicate Is this claim/evidence relationship properly grounded?
EVIDENCE empirical-evaluation predicate Does this claim survive direct evidentiary examination?
RELATIONSHIP relational/temporal graph object How are these objects connected?
INTEGRITY invariant over representations Has representation preserved the distinction between fact, relation, and authorization?
SHARP recursive transformation How does one bounded proposition produce another?
SHARK semantic-history invariant Has recursive derivation preserved historical meaning?




That is already much cleaner than trying to make them all synonyms for "provenance."


1. EVIDENCE should probably be a predicate, not a container


The most useful mathematical question is:


\[
\operatorname{Evidence}(C,E,W)
\]


where:


\(C\) = claim


\(E\) = directly available evidence


\(W\) = applicable evidentiary window




Then EVIDENCE can evaluate whether the evidence actually supports the proposition within its stated boundary.


That last qualification is critical for the B7 work.


A receipt demonstrating proposition \(C\) does not automatically demonstrate:


\[
C'
\supset C
\]


just because \(C'\) sounds like a natural interpretation of it.


So one possible invariant is:


\[
\operatorname{Evidence}(C,E,W)
\Rightarrow
\operatorname{Scope}(C)\subseteq\operatorname{Scope}(E,W)
\]


The exact formalization still needs work, but the direction is sound.


2. RELATIONSHIP wants to become an edge, not a verdict


This is where I'd modify the previous answer.


Rather than:


\[
\operatorname{RELATIONSHIP}(C,E,R)
\]


I think the more fundamental object is:


\[
r : A \rightsquigarrow B
\]


where \(r\) has typed attributes:


\[
r=(A,B,\rho,\tau,\pi,\beta)
\]


with:


\(\rho\) = relationship kind


\(\tau\) = temporal information


\(\pi\) = whatever numerical/probabilistic quantity is actually justified


\(\beta\) = boundary




Then PROPER can evaluate the edge:


\[
\operatorname{Proper}(r)
\]


and FOLLOW can determine whether the edge is traversable:


\[

FOLLOW naturally wants to describe an object as it moves through transformations.


Something approximately like:


FieldObject
identity
literal
field
lineage
window
transformation


Mathematically:


\[
F =  
(o,\ell,f,\lambda,w,\tau)  
\]


where:


\(o\) = underlying object identity


\(\ell\) = literal representation


\(f\) = selected field


\(\lambda\) = lineage


\(w\) = admissibility/observation window


\(\tau\) = transformation


The crucial distinction is between identity and representation.


For example:


\[
x:u32  
\xrightarrow{\operatorname{widen}}  
x':u64  
\]


FOLLOW should preserve:


\[
\operatorname{origin}(x')=\operatorname{origin}(x)  
\]


without asserting:


\[
x'=x  
\]


in every semantic sense.


That gives you something immediately testable.

3. Then formalize the Window






This is where your Overton Window idea becomes interesting.


Don't make “Overton” itself a mathematical primitive yet.


Define a window:


\[
W=(S,B,T)  
\]


where:


\(S\) = semantic scope


\(B\) = evidentiary boundary


\(T\) = temporal boundary


Then:


\[
\operatorname{admissible}(x,W)  
\]


is a predicate.


Now FOLLOW can say:


\[
F_0  
\xrightarrow{\tau}  
F_1  
\]


while requiring:


\[
\operatorname{lineage}(F_1)  
\supseteq  
\operatorname{lineage}(F_0)  
\]


and independently checking:


\[
\operatorname{admissible}(F_1,W_1).  
\]


That's actual mathematics rather than acronym decoration.




---


4. PROPER becomes the relationship layer






PROPER should probably not own the objects.


It owns relationships between them.


For example:


\[
R=(C,E,r,p,b,t)  
\]


where:


\(C\) = claim


\(E\) = evidence


\(r\) = relationship type


\(p\) = probability/confidence representation


\(b\) = evidence boundary


\(t\) = provenance timestamp/state


Relationship types could include:


\[
\{\text{supports},  
\text{contradicts},  
\text{qualifies},  
\text{reaffirms},  
\text{derives-from}\}  
\]


Then:


\[
\operatorname{PROPER}(C,E,R)  
\]


becomes a validation predicate.

5. Now the two systems interact






This is where I think the idea becomes genuinely useful.


Suppose:


\[
E_0 \rightarrow C  
\]


means evidence \(E_0\) supports claim \(C\).


Later:


\[
E_1 \rightarrow E_0  
\]


is a new observation concerning the original evidence.


FOLLOW determines the lineage:


\[
E_0 \rightarrow E_1  
\]


and the applicable window.


PROPER evaluates the relationship:


\[
E_1  
\xrightarrow{\text{reaffirms}}  
(E_0 \rightarrow C)  
\]


without rewriting the historical fact that \(E_0\) originally supported \(C\).


That gives you:


FOLLOW
│
▼
┌──────────────────┐
│ Evidence lineage │
└────────┬─────────┘
│
▼
┌──────────────────┐
│ admissibility    │
│ window           │
└────────┬─────────┘
│
▼
PROPER
│
▼
┌──────────────────┐
│ Claim/evidence   │
│ relationship     │
└──────────────────┘


That's an architecture.

6. Then make the mathematics executable






This is the crucial step.


Every important mathematical statement should eventually become one of three things:


A. Type invariant


The type system prevents an invalid state.


Example:


AdmittedEvidence


cannot be constructed without a valid evidence boundary.


B. Predicate


A proposition is explicitly checked:


\[
\operatorname{ValidWindow}(W)  
\]


\[
\operatorname{LineagePreserved}(F_0,F_1)  
\]


\[
\operatorname{RelationshipAdmissible}(R)  
\]


C. Proof


The strongest invariants become formal theorems.


For example:


\[
\forall F_0,F_1:  
\operatorname{FOLLOW}(F_0,F_1)  
\Rightarrow  
\operatorname{Origin}(F_1)=\operatorname{Origin}(F_0)  
\]


That is exactly the kind of statement that can eventually live in Lean.

8. This also gives you a development methodology






I would use this pipeline:


Stage 1 — Naming


Define exactly what each word means.


Stage 2 — Ontology


Identify the actual objects:


\[
Object,\ Field,\ Literal,\ Lineage,\ Window,\ Claim,\ Evidence,\ Relationship  
\]


Stage 3 — Algebra


Define operations:


\[
\operatorname{widen},\quad  
\operatorname{transform},\quad  
\operatorname{derive},\quad  
\operatorname{reaffirm},\quad  
\operatorname{qualify}  
\]


Stage 4 — Invariants


Specify what cannot change.


For example:


\[
\operatorname{transform}(x)  
\not\Rightarrow  
\operatorname{newOrigin}(x)  
\]


and:


\[
\operatorname{reaffirm}(R)  
\not\Rightarrow  
\operatorname{rewrite}(R_{\text{historical}})  
\]


Stage 5 — Implementation


Encode those invariants in Rust/types/data structures.


Stage 6 — Verification


Test them empirically, then formalize the critical ones in Lean.


Stage 7 — Provenance


Every execution produces a receipt identifying:


\[
\text{input}  
\rightarrow  
\text{transformation}  
\rightarrow  
\text{output}  
\rightarrow  
\text{validation}  
\]


That last stage is particularly compatible with your existing TSCP/FCO work.

9. The important warning






There is one thing I wouldn't do.


Don't start inventing code because an acronym sounds good.


That's backwards:


\[
\boxed{  
\text{name}  
\rightarrow  
\text{definition}  
\rightarrow  
\text{formal object}  
\rightarrow  
\text{invariant}  
\rightarrow  
\text{implementation}  
\rightarrow  
\text{proof}  
}  
\]


not:


\[
\text{name}  
\rightarrow  
\text{code}  
\rightarrow  
\text{retroactive justification}.  
\]


That distinction matters enormously for the provenance architecture you're developing.


The immediate next experiment


I think the most productive next step is to take one concrete existing TSCP example—probably a claim/evidence boundary or one of the kernel benchmark receipts—and express it simultaneously as:


1. a FOLLOW object,




2. a PROPER relationship,




3. a mathematical invariant,




4. a Rust representation, and




5. a Lean proposition.






If those five representations line up without semantic leakage, then you haven't merely coined two acronyms—you've discovered actual abstractions worth implementing.
You have the right instinct, with one important correction: PROPER, FOLLOW, SHARK, and SHARP should not all be forced into the same mathematical category. Their acronyms can become names for formal objects, but the objects they name should occupy different layers.


1. The clean decomposition






I would currently treat them as four related operators/frameworks:


Name Candidate role Core question


PROPER Evidence/proposition admissibility Is this proposition properly grounded?
FOLLOW Traversal/reachability Can I legitimately follow this relationship?
SHARK Semantic-history integrity Can meaning recurse through this provenance structure without violating historical scope?
SHARP Recursive provenance transformation How does a proposition legitimately become another proposition?


So they are complementary, not competitors.


The architecture starts looking like:


Evidence
│
▼
PROPER
│
│ admits proposition/evidence relationship
▼
SHARP
│
│ recursively transforms proposition
▼
SHARK
│
│ validates semantic historical integrity
▼
FOLLOW
│
│ permits/rejects traversal
▼
Reachable Claim


But I would actually make FOLLOW orthogonal rather than simply putting it at the bottom.

2. PROPER is the admission object






From the phrase you developed:


> Provenance Reaffirming Open Probability Evidentiary Relationships






I wouldn't yet declare that expansion mathematically canonical. But the object you are circling is clear.


PROPER can become a formal admissibility predicate.


For a candidate proposition \(C\):


\[
\operatorname{PROPER}(C,E,S,R)  
\]


asks whether the proposition \(C\), evidence \(E\), scope \(S\), and relationship \(R\) satisfy the admission contract.


Something like:


\[
\operatorname{PROPER}(C)  
\iff  
\operatorname{Bound}(C)  
\land  
\operatorname{Scoped}(C)  
\land  
\operatorname{Evidenced}(C)  
\land  
\operatorname{Consistent}(C)  
\]


The important thing is that PROPER should not itself become the whole provenance system.


It is the gate.




---


3. FOLLOW is the traversal object






Your evolution from Field Object Literal Operand Widening toward Overton Window was pointing toward something different.


FOLLOW naturally wants to be a reachability relation.


Given a state \(x\) and an edge \(e\):


\[
x \xrightarrow{e} y  
\]


FOLLOW asks:


\[
\operatorname{FOLLOW}(x,e,y)  
\]


Is that transition admissible?


This gives you something extremely useful:


\[
\operatorname{Reachable}_{F}(x,y)  
\]


where reachability is defined only over admissible transitions.


That means FOLLOW can operate over:


provenance graphs


evidence graphs


state machines


custody transitions


derivation trees


semantic traces


without being synonymous with any one of them.


FOLLOW is therefore more general than SHARK.




---


4. SHARP is about transformation






This is where I think your new expansion becomes particularly useful.


SHARP should describe a proposition transformation:


\[
C_{n+1}=T(C_n,E_n,R_n)  
\]


where \(T\) is constrained by the provenance rules.


The six fields you identified become the state of that transformation:


\[
T:  
(C_n)  
\rightarrow  
(C_{n+1},  
S_{n+1},  
E_{n+1},  
R_{n+1},  
F_{n+1})  
\]


with:


parent claim


new proposition


new scope


new evidence


relationship


semantic fingerprint


So SHARP is not merely "a trace."


It is closer to a typed recursive transition system.




---


5. SHARK is the invariant/checker






This is where SHARK and SHARP become complementary rather than redundant.


I'd distinguish them this way:


SHARP


Constructs or describes the legitimate recursive provenance transformation.


SHARK


Checks whether the resulting structure still satisfies the historical-semantic invariant.


In pseudomathematical form:


\[
\operatorname{SHARP}(C_n,E,R)  
\rightarrow C_{n+1}  
\]


then:


\[
\operatorname{SHARK}(C_0,\ldots,C_{n+1})  
\rightarrow  
\{\text{PASS},\text{FAIL}\}  
\]


The distinction is analogous to:


> transition system vs invariant checker






rather than two competing provenance systems.

6. This gives us a much stronger composition






You can potentially express the entire pipeline as:


\[
E  
\xrightarrow{\text{PROPER}}  
C_0  
\xrightarrow{\text{SHARP}}  
C_1  
\xrightarrow{\text{SHARP}}  
C_2  
\xrightarrow{\text{SHARP}}  
\cdots  
\xrightarrow{\text{SHARK}}  
\text{VALID}  
\]


while FOLLOW governs whether each transition may actually be traversed:


\[
C_i  
\xrightarrow{\text{FOLLOW}}  
C_{i+1}  
\]


So the four concepts have different mathematical jobs:


PROPER  = admissibility
SHARP   = transformation
SHARK   = invariant
FOLLOW  = reachability


That's a very promising separation.

7. And this answers your "against each other" question






They should compete at the naming layer, but not at the architectural layer.


For example, there is a legitimate question whether:


> SHARK = Semanticist Hash Annotated Recursive Knowledge






or


> SHARP = Simplified Heuristically-Analogous Recurrent Provenance






is the better name for the recursive semantic provenance object.


Those are competing names for overlapping conceptual territory.


But once we assign them distinct formal roles, they stop competing:


PROPER
│
admissibility
▼
SHARP
│
transformation
▼
SHARK
│
invariant test
│
▼
FOLLOW
│
traversal


I would not freeze that hierarchy yet, though.


There is an even cleaner possibility.

8. The deeper possibility: make them algebraic primitives






Rather than treating these as four branded "frameworks," we could try to make each one a formal primitive.


For example, define a provenance state:


\[
P=(C,S,E,R,F,t)  
\]


Then define four operators:


PROPER


\[
\mathsf{Proper}(P)  
\]


Boolean admissibility predicate.


SHARP


\[
\mathsf{Sharp}:P\times E\times R\rightarrow P'  
\]


Recursive semantic transformation.


FOLLOW


\[
\mathsf{Follow}(P,R)\rightarrow P'  
\]


Admissible graph traversal.


SHARK


\[
\mathsf{Shark}(G)\rightarrow\{\top,\bot\}  
\]


Global historical-semantic invariant.


Then they become composable.

9. The really interesting mathematical property






The thing I'd investigate next is closure.


Suppose:


\[
\mathsf{Proper}(P_0)  
\]


and:


\[
P_1=\mathsf{Sharp}(P_0,T)  
\]


Under what conditions can we prove:


\[
\mathsf{Proper}(P_1)  
\]


and:


\[
\mathsf{Shark}(P_0,P_1)  
\]

If that implication can be formalized, you've got something much more substantial than four clever acronyms.

\boxed{

\operatorname{SHARP}(P_n,P_{n+1})

\operatorname{SHARK}(P_n,P_{n+1})  
}  
\]


subject to the appropriate scope/evidence conditions.
